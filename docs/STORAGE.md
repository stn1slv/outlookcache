# Outlook for Mac local storage (Phase 0 findings)

Discovered on one machine on 2026-11-24. The format is undocumented and can change with any Outlook update. Confidence labels: **verified** (checked on this machine, usually by a controlled experiment), **likely** (consistent with all observations, not proven), **unknown**.

The container layer follows the public specification by securized, [hxstore-reverse-engineering](https://github.com/securized/hxstore-reverse-engineering) (MIT, tested on 16.107.1). Everything below the container layer (object framing, version stamp, read state, flag, folders) is new work from this project.

## Container: blocks

| Item | Finding | Confidence |
|---|---|---|
| Header | Magic `Nostromo`, version byte `i` at +8, page size 4096 at +0x38. | verified |
| Blocks | 40-byte header: CRC-32 of header bytes `[4,0x20)`, CRC-32 of `[8, end)`, magic `05 6a 70 3b 64 45 02 5d`, type u32, compressed length, decompressed length, constant 4, then **u64 key at +0x20**. Payload is one LZ4 block. | verified |
| Key at +0x20 | Equals the ID in the first object framing when the payload starts with one (5,345 of 5,345 such blocks; the other blocks start with a multi-object header). The spec lists this field as unresolved. | verified |
| Validity | First snapshot: 17,682 candidates, 17,639 valid, 43 invalid; identical across plain copies and APFS clones, so not caused by copying. Later snapshot: 138 invalid, of which 130 are **type 16 with a payload CRC mismatch** and 8 fail the header CRC (their type field cannot be trusted). **Type 16 is a second record stream:** the count grew from 130 (first snapshots) to 1,122 and then 1,205 (two later snapshots) while Outlook ran; new type-16 blocks are appended in bursts (83 during one Junk cleanup), all 118 bytes compressed and 472 bytes declared, with only 3 distinct key values in the file, none of them an object ID. No type-16 payload decodes as LZ4 (0 of 1,205), so the format is different or encrypted. Only 3 of 1,122 matched the old any-position index test (its false-positive rate), no existing block turned into type 16 in place, and the unread counts match the UI without them. Probably a journal or log. Their integrity cannot be checked until the format is known. A reader should count them separately (for example `undecoded_blocks`) instead of as damaged sections, and say that their content is not read. | verified (counts), likely (not message records), unknown (format, integrity) |
| Versions | The store keeps old versions of each object. A key can appear in 10 or more valid blocks. CRC validity does not mean "current"; see the live-block index below. | verified |
| Header fields | u64 at +0x58 = `0x25000` and +0x78 = `0x75000`: block index areas A and B, `0x50000` bytes each. **+0x68 = two u32 counts: index entries and overflow buckets** (for example 15,303 and 1,583; they change at each index write). +0x48 = `0xfff1` (65,521, a prime; probably the hash modulus) and +0x28 = `0x12c0`; bit 32 of both toggles between writes (probably the A/B switch). +0x18 = `0x5000` and +0x20 = `0xc5000` probably bound the region `[0x5000, 0xc5000)`; the 128 KB before area A is not decoded (not a simple allocation bitmap). Blocks start after this region. | verified (values, counts), likely (meaning of +0x28, +0x48) |
| Block index | Each area is a **hash table of 65,536 slots of 5 bytes** (65,536 x 5 = `0x50000`). A used slot holds a u32 (block offset / 256) and a size byte = ceil((0x28 + compressed length) / 512) (true for 12,015 of 12,057 slots). Areas A and B hold the same entries in one snapshot; in a later one (h3) 104 slots differ, so which area is current is open. The reader uses area A and reports the number of differing slots as `index_areas_differ`. The key is not stored, and no common hash (CRC-32, FNV, multiplicative, MD5, SHA-1 and others) maps the block key to its slot, so lookups by key are not possible yet. **Direct slots:** 12,057 of 13,640 used slots point exactly at a type-8 block start. **Overflow:** the other used slots (exactly the second header count, 1,583) have size byte 1 and point at space that holds no matching data, also right after an index write; together with the first count (15,303 entries) this fits about 3,250 entries in about 1,600 collision buckets (about 2 per bucket, as expected for this load), stored somewhere not found (not in the raw file and not in any decoded payload as the 5-byte entry). **Consequence:** the direct slots cover about 79% of the entries. Live blocks reachable only through an overflow bucket look "not indexed": in the probe check, three Sent items, one live draft and two Deleted Items copies had no direct slot, while the purged Junk item also had none. So "not in a direct slot" means "deleted or in overflow". The earlier "any byte position" membership test (55% match, 0.32% false positives) is replaced by exact slot parsing (no false positives). The index is written at checkpoints and lags behind new blocks. **Current copy rule:** the copy with the highest stamp; on a stamp tie, a copy in a direct slot (the first one when several are); ambiguous when the candidates (the tied direct copies, or all tied copies when none is direct) differ in status or folder. In two snapshots only 1 item had a direct-slot copy older than another copy (a change after the checkpoint), so the stamp, not the slot, decides. **Confirmed** = the chosen copy is in a direct slot. **Deleted messages:** not decidable until the overflow storage is found. Arithmetic: overflow holds 21% of entries and 22% of items are unconfirmed (752 of 3,366), which fits about 700 live and about 50 deleted items in the unconfirmed group. **v1 decision (gate, 2026-11-25):** list unconfirmed items by default, mark each message `confirmed: true/false`, and count unconfirmed items in the response envelope; never drop them. **Damage:** a failing block in a direct slot is reported as damage; a failing block without a direct slot is counted as `unindexed_damaged`, because it is usually an old copy but can be a live block in an overflow bucket. If the header has no usable index, the reader still loads and marks every message unconfirmed (`index_unreadable`). | verified (slot layout, size byte, counts), unknown (hash, overflow storage) |

| Folder objects | Several small objects per folder ID (types `0x3d`, `0x1e3`, `0x1cc`) plus a large `0xd6` object (probably the message list), all with class `0x4d` and the account root as owner. | likely |

| Account roots | `0x18757896` (account A) and `0x18757ba5` (account B) own the folders of each account. `0x18757694` (A) and `0x1875791b` (B) are a second per-account object, referenced at +380 of every message and next to folder entries. | verified (roots), likely (second object) |
| Account to `Files/S0/<n>` | Objects of an account store absolute file paths as UTF-16 text: the account B root (`0x02e0` object) holds `.../Files/S0/2948/EFMData/<n>.dat` paths, and blocks of account A objects hold `.../Files/S0/2/...` paths. | Folder records and hierarchy | A parent's folder list (the account root's, or a parent folder's, `0x01e3` and `0x0002` objects) holds one record per child folder: `e3 01`, 8 zero bytes, **parent ID** (u64), a Windows collation sort key (pairs `0e xx`, separators `01`, ending with one `00` byte), the **display name** as UTF-16LE ending with `00 00`, then (form 1) `01`, 4 bytes, `05 00 d8 04`, 4 bytes, `00 00 4d`, 9 zero bytes, **folder ID**, u32 2, account root. ## Snapshot method

| Method | Result | Confidence |
|---|---|---|
| Streaming copy (`os.Open` read-only, copy to `os.MkdirTemp` 0700, retry when size or mtime changes) | Consistent: same block and damage counts as the clone. About 50 ms for 117 MB when the file is in the page cache. | verified |
| APFS clone (`cp -c`) | Same result, 30 ms. Needs `clonefile(2)`; not in the Go standard library. | verified |
| Decision | Streaming copy. No extra dependency. Size and mtime are checked on the open file before and after the copy (3 attempts). The per-block CRCs catch a torn block, but not a copy that mixes valid blocks written at different moments; with 138 standing CRC failures, a new failure caused by copying cannot be told apart either. | decision |

The live file changed between snapshots taken seconds apart, even with no user action (a stamp field changed in every copy).

## Body coverage

| Tier | Finding | Confidence |
|---|---|---|
| Body record | The item's own block (block key = item ID) starts with an unframed record before the first object framing. It holds the item class as UTF-16 at +1893 of the payload in most blocks (in about 55% of blocks (1,883 of 3,445 in b1) the whole record starts later; all offsets below are relative to the class). **u32 at class -210: flags in the high byte, body size in the low 24 bits.** Flag `0x80` = inline HTML, `0x82` = body in `EFMData`, 0 = no body stored. u32 at class -202 has the same form for a second HTML field; u32 at class -214 is the size of a field that can precede the body. | verified (probes; whole store, snapshot b1) |
| Inline HTML | After the class come fields without terminators: usually the body, then other fields and a second copy of the body. In some records a `<div>` fragment comes first (a draft's editor text, for example); its size is at class -214 or -202, or not found. **Rule:** the body is the first whole HTML document (UTF-8, starts with a tag, ends with `</html>` plus white space) of the stated size at one of these starts: the first UTF-8 field after the class, that start plus the sizes at -214 and -202, or a window that ends at a `</html>`. Snapshot b1: 3,129 messages have flag `0x80`; the rule finds a whole document for all of them (2,847 at the first field, 101 after a sized fragment, 181 by the end tag). | verified (whole store) |
| `EFMData` | Flag `0x82`: 216 messages in b1. The head holds the absolute paths of the body files (1, 2 or 4 paths, 2 distinct files at most). Both files of a message hold the same HTML after gunzip (164 of 164 pairs). All are gzip, >= 64 KB and whole HTML documents; 2 files are missing on disk. The reader keeps only the folder number and the file name (checked patterns) and opens the file read-only through an `os.Root` at `Files/S0`. | verified (whole store) |
| No body | Flag 0: 100 messages in b1 (preview only). | verified |

## Privacy notes for development

- `hxdiscover` (dev tool, not shipped) prints counts, offsets, hex of binary bytes and redacted shapes of text. Hex output masks every span that decodes as UTF-16LE or UTF-8 text in scripts below U+2000 (Latin, Cyrillic, Greek, Arabic, Hebrew and others). CJK and Hangul text is **not** detected, because object IDs often decode to CJK code points.
- Text is printed only from the `oc-probe` marker onward, and only while it stays in the synthetic character set (lower-case letters, digits, space and `-.:,_`); markers must start with `oc-probe`. Exact times of recent ticks are printed only with `-ticks`.
- `namefind` and `addrcount` take a real name or address only from the environment variable `HXD_MATCH` (not a flag, so it stays out of shell history and the process list); `tree` marks rows that equal it. They print only IDs, types, offsets, counts, a validated prefix kind and "equals" markers, never the text or the raw bytes next to it. `tree` prints a folder name only when it is a schema word or a strict probe name (`oc-probe-[a-z0-9-]+`). `fieldcmp` masks every u16 that decodes as a letter or digit in any script.
- Two commands written during this stage were removed after review because they could print real text: `keys` (words common to many objects, which include names and addresses) and `head` (raw payload dump, where the redactor misses CJK text).
- `bytecand` and `ticks` accept only a probe target (a UTF-16 string that starts with the marker, optionally after `RE:`); `ticks` also needs `-ticks` and covers only the last 7 days. `bytecand` leaves out every object that has text at the compared offset.
- Real account addresses and real folder names were typed into `namefind`, `addrcount` and `tree` commands during discovery, so they appear in the local terminal and session transcript (not in the repository, not in tool output). Later runs pass them through `HXD_MATCH`.
- Three incidents during discovery, all fixed in the tool: item-class strings glued to a following name field printed about 150 display names; a hex probe printed part of the user's own name as UTF-16 hex; a misparsed folder entry printed the user's own display name next to probe text.
