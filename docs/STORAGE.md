# Outlook for Mac local storage (Phase 0 findings)

Discovered on one machine on 2026-11-24. The format is undocumented and can change with any Outlook update. Confidence labels: **verified** (checked on this machine, usually by a controlled experiment), **likely** (consistent with all observations, not proven), **unknown**.

The container layer follows the public specification by securized, [hxstore-reverse-engineering](https://github.com/securized/hxstore-reverse-engineering) (MIT, tested on 16.107.1). Everything below the container layer (object framing, version stamp, read state, flag, folders) is new work from this project.

## Container: blocks

| Item | Finding | Confidence |
|---|---|---|
| Header | Magic `Nostromo`, version byte `i` at +8, page size 4096 at +0x38. | verified |
| Blocks | 40-byte header: CRC-32 of header bytes `[4,0x20)`, CRC-32 of `[8, end)`, magic `05 6a 70 3b 64 45 02 5d`, type u32, compressed length, decompressed length, constant 4, then **u64 key at +0x20**. Payload is one LZ4 block. | verified |
| Key at +0x20 | Equals the ID in the first object framing when the payload starts with one (5,345 of 5,345 such blocks; the other blocks start with a multi-object header). The spec lists this field as unresolved. | verified |
| Validity | First snapshot: 17,682 candidates, 17,639 valid, 43 invalid; identical across plain copies and APFS clones, so not caused by copying. Later snapshot: 138 invalid, of which 130 are **type 16 with a payload CRC mismatch** and 8 fail the header CRC (their type field cannot be trusted). **Type 16 is a second record stream:** the count grew from 130 (first snapshots) to 1,122 and then 1,205 (two later snapshots) while Outlook ran; new type-16 blocks are appended in bursts (83 during one Junk cleanup), all 118 bytes compressed and 472 bytes declared, with only 3 distinct key values in the file, none of them an object ID. No type-16 payload decodes as LZ4 (0 of 1,205), so the format is different or encrypted. Only 3 of 1,122 matched the old any-position index test (its false-positive rate), no existing block turned into type 16 in place, and the unread counts match the UI without them. Probably a journal or log. Their integrity cannot be checked until the format is known. A reader should count them separately (for example `undecoded_blocks`) instead of as damaged sections, and say that their content is not read. | verified (counts), likely (not message records), unknown (format, integrity) |
| Versions | The store keeps old versions of each object. A key can appear in 10 or more valid blocks. CRC validity does not mean "current"; see the live-block index below. | verified |
| Header fields | u64 at +0x58 = `0x25000` and +0x78 = `0x75000`: block index areas A and B, `0x50000` bytes each. **+0x68 = two u32 counts: index entries and overflow buckets** (for example 15,303 and 1,583; they change at each index write). +0x48 = `0xfff1` (65,521, a prime; probably the hash modulus) and +0x28 = `0x12c0`; bit 32 of both toggles between writes (probably the A/B switch). +0x18 = `0x5000` and +0x20 = `0xc5000` probably bound the region `[0x5000, 0xc5000)`; the 128 KB before area A is not decoded (not a simple allocation bitmap). Blocks start after this region. | verified (values, counts), likely (meaning of +0x28, +0x48) |
| Block index | Each area is a **hash table of 65,536 slots of 5 bytes** (65,536 x 5 = `0x50000`). A used slot holds a u32 (block offset / 256) and a size byte = ceil((0x28 + compressed length) / 512) (true for 12,015 of 12,057 slots). Areas A and B hold the same entries. The key is not stored, and no common hash (CRC-32, FNV, multiplicative, MD5, SHA-1 and others) maps the block key to its slot, so lookups by key are not possible yet. **Direct slots:** 12,057 of 13,640 used slots point exactly at a type-8 block start. **Overflow:** the other used slots (exactly the second header count, 1,583) have size byte 1 and point at space that holds no matching data, also right after an index write; together with the first count (15,303 entries) this fits about 3,250 entries in about 1,600 collision buckets (about 2 per bucket, as expected for this load), stored somewhere not found (not in the raw file and not in any decoded payload as the 5-byte entry). **Consequence:** the direct slots cover about 79% of the entries. Live blocks reachable only through an overflow bucket look "not indexed": in the probe check, three Sent items, one live draft and two Deleted Items copies had no direct slot, while the purged Junk item also had none. So "not in a direct slot" means "deleted or in overflow". The earlier "any byte position" membership test (55% match, 0.32% false positives) is replaced by exact slot parsing (no false positives). The index is written at checkpoints and lags behind new blocks. **Current copy rule:** the copy with the highest stamp; on a stamp tie, the copy in a direct slot; ambiguous when tied copies differ in status or folder and the index does not decide. In two snapshots only 1 item had a direct-slot copy older than another copy (a change after the checkpoint), so the stamp, not the slot, decides. **Confirmed** = the chosen copy is in a direct slot. **Deleted messages:** not decidable until the overflow storage is found. Arithmetic: overflow holds 21% of entries and 22% of items are unconfirmed (752 of 3,366), which fits about 700 live and about 50 deleted items in the unconfirmed group. **v1 decision (gate, 2026-11-25):** list unconfirmed items by default, mark each message `confirmed: true/false`, and count unconfirmed items in the response envelope; never drop them. | verified (slot layout, size byte, counts), unknown (hash, overflow storage) |

| Framing | `06 00 70 05`, u64 object ID, u16 type, u32 length, then fields. Next comes `90 02`, the ID again, a u16 class (`0x4d` = folder) and the owner ID. 49,750 framings found, all lengths fit inside their payload. | verified |
| Payload header | 16 bytes before the first object, for example `00000000 00000000 01000000 <len-16>`. A second header style (`02000000 ...`) holds several objects. | likely |
| Object IDs | u64, values around `0x1875xxxx` to `0x1880xxxx`; new objects get higher IDs. References to other objects are raw u64 IDs. The tools treat `[0x18000000, 0x19000000)` as the ID range; this range comes from one store and will not fit other profiles or a store that grows past it (UNVERIFIED). The reader needs a range taken from the store itself. | verified (values), unknown (general range) |
| Strings | In items, after the anchor `[item ID][00 00 c7 00 + 8 zero bytes][conversation ID]`, a run of NUL-terminated UTF-16LE strings (found in 100% of items). The run has no fixed order and holds only present properties (two main layouts; sent items and replies carry extra strings such as reply links). **A length table in the fixed part gives each property's size** (u16 = UTF-16 bytes + 2, 0 or 2 when absent): sender address +1648, sender name +1640, item class +1488, Message-ID +1480, preview +1556, subject +1512 (normalized, without `RE:`), conversation topic +1684. **Rule:** the class is the first string starting with `IPM.` or `REPORT.`; every other field is the first unused string whose size matches its entry (sender before the class; Message-ID and preview after it; subject and topic after it first, then before it); when no string matches the subject entry, the topic is used. Found with probes 6 and 7 (external sender) and checked on 3,443 items: class 99.9%, sender address 99.0% (the rest have none), Message-ID 98.9%, sender name 98.8%, subject 98.7% (325 of them from the topic), preview 2,884 plus 550 with no preview; all 18 probe items give the right subject. Other entries (+1636, +1644, +1668, +1500 and more) belong to extra strings not mapped yet (probably sent-representing sender and display lists). | verified (probes and population) |
| Message and conversation objects | Type `0xc7`, in two forms. **Correction (reply probe):** the form with an account ID at +32, called "message form" in earlier notes, is the **conversation** object; the form without it ("parent form") is the **message item**. Proof: the reply item and the original item both point at +436 to the same conversation-form ID, in both accounts. A conversation has the same fields 10 bytes higher (folder +1166, status +1772, stamp +370) and follows its latest item, which is why single-message tests worked on it. Item IDs found in valid blocks (deleted ones included, so the number changes as Outlook reuses space): 4,041 items in 2,803 conversations in one snapshot, 3,364 in 2,267 in a later one. **The reader must list items, not conversations.** Offsets in the field table below are conversation-form offsets; subtract 10 for items (folder +1156, status +1762, stamp +360). | verified (reply probe) |
| Folder objects | Several small objects per folder ID (types `0x3d`, `0x1e3`, `0x1cc`) plus a large `0xd6` object (probably the message list), all with class `0x4d` and the account root as owner. | likely |
| Folder names (older entry format) | Entries `4d` + 9 zero bytes, folder ID, `2`, owner, folder ID, owner, 4 zero bytes, length-prefixed name. Found only for a few folders. The earlier claim that standard folders have no stored name was wrong: see Folder records. | verified (few folders) |
| Account roots | `0x18757896` (account A) and `0x18757ba5` (account B) own the folders of each account. `0x18757694` (A) and `0x1875791b` (B) are a second per-account object, referenced at +380 of every message and next to folder entries. | verified (roots), likely (second object) |
| Account to `Files/S0/<n>` | Objects of an account store absolute file paths as UTF-16 text: the account B root (`0x02e0` object) holds `.../Files/S0/2948/EFMData/<n>.dat` paths, and blocks of account A objects hold `.../Files/S0/2/...` paths. So A = `S0/2`, B = `S0/2948`. `S0/1` holds only `NonPersisted`. | verified |
| Account address | Not found as a field of the account objects (both addresses sit in one shared settings object of type `0x4007`, layout unknown). Rule that works: the address contained in every message of the account's Sent folder (slot +1549). Population check on message items (current copy rule, deleted ones included): 406 of 406 items in Sent of A contain A's address, 157 of 157 in Sent of B contain B's address; the other address is in 11 and 1 of them. Account type (Exchange, Outlook.com, IMAP) is not found. | verified (rule), unknown (type) |
| Standard folder slots | The block of an account root starts with an unframed record (about 2 KB before the first framing). It holds references `[type u16][8 zero bytes][ID][u32 2][owner][ID][owner]` at fixed offsets, so **the offset of the slot gives the folder role**. Both accounts use the same offsets. Verified roles: +861 = Inbox (probe mails received in A and B), +1549 = Sent (probe mails sent from A and B). +477 = Drafts (a new unsent `oc-probe-draft` in account A was stored in the +477 folder). +1205 = Outbox, from the move of one sent probe Drafts → Outbox → Sent (account A only). +429 = Deleted Items (a deleted probe moved there). +909 = Junk Email (a probe dragged to Junk moved there). +285 = Archive (a probe archived with the Archive button moved there). Not yet labelled: +621, +1397, +1445 (A only); the UI shows Conversation History in both accounts and Snoozed and RSS Subscriptions only in account A, so one of the two B slots is a folder the UI does not show. | verified (Inbox, Sent, Drafts, Deleted, Junk, Archive; account A, and Inbox and Sent in B), likely (Outbox), unknown (others) |
| Folder records and hierarchy | A parent's folder list (the account root's, or a parent folder's, `0x01e3` and `0x0002` objects) holds one record per child folder: `e3 01`, 8 zero bytes, **parent ID** (u64), a Windows collation sort key (pairs `0e xx`, separators `01`, ending with one `00` byte), the **display name** as UTF-16LE ending with `00 00`, then (form 1) `01`, 4 bytes, `05 00 d8 04`, 4 bytes, `00 00 4d`, 9 zero bytes, **folder ID**, u32 2, account root. Verified: the probe folder name; a user folder of account A holding its six subfolders, matched to the UI by name and by the unread count (the subfolder with the one unread message is `0x1875ab71`). Standard folders store English names (`Inbox`, `Drafts`, `Sent Items`, `Deleted Items`, `Archive`, `Junk Email`) that agree with the role slots. Form 2 records have the same head but no folder ID after the name (the next object header belongs to a different folder); four empty user folders and some standard ones (Outbox, Conversation History, Snoozed, RSS Subscriptions) were only found in this form or not at all. The older entry format (`4d` + 9 zero bytes + ID ... `0x80000000|len` name) gives ID and name for a few of them (one empty user folder of account B is `0x1875ac04`). Every folder that holds live messages in the last snapshot has a form 1 name and parent. The store keeps old versions of these records, so a version from a block in the live-block index wins, and folders whose indexed versions disagree are reported (0 in the last snapshot). | verified (form 1, on folders with messages), unknown (form 2 IDs) |
| Favorites list | Type `0x0163` of the second per-account object holds an ordered list of folder references (Inbox, Sent, then other folders). It differs per account, so it is a user list (probably Favorites), not a role table. | likely |
| Other types | Owned by a message item ID: `0xcc` To, `0xcd` Cc, `0xce` Bcc, `0x168` attachments (see Message fields); `0x154` (always the smallest size) and `0x2f6` (always 181 bytes) come in the same group, meaning unknown. `0x04`: one new object appeared when a message was moved, meaning unknown. | verified (0xcc, 0xcd), likely (0xce, 0x168), unknown (others) |

## Message fields (`0xc7`)

Offsets are from the start of the object framing and are given for both forms: **item** (the message; the reader uses this) and **conversation** (10 bytes higher). Rows marked "before the correction" were measured on conversation objects.

|---|---|---|
| Version stamp | 6 bytes, item +360, conversation +370, little-endian. It **sometimes does not change** on a status change: after the user marked about 20 probe conversations read, 19 IDs had copies with the same highest stamp and different read bits; on the reply probe, mark-read and mark-unread did change the stamp of both the item and the conversation. So stamp ties must be handled (see Live-block index). 848 conversation IDs have stamp 0 in every copy. The value is not unique per write; successive values differ by about N x 10^9. | verified (both behaviours seen), unknown (when each happens) |

|---|---|---|

## Privacy notes for development

- `hxdiscover` (dev tool, not shipped) prints counts, offsets, hex of binary bytes and redacted shapes of text. Hex output masks every span that decodes as UTF-16LE or UTF-8 text in scripts below U+2000 (Latin, Cyrillic, Greek, Arabic, Hebrew and others). CJK and Hangul text is **not** detected, because object IDs often decode to CJK code points.
- Text is printed only from the `oc-probe` marker onward, and only while it stays in the synthetic character set (lower-case letters, digits, space and `-.:,_`); markers must start with `oc-probe`. Exact times of recent ticks are printed only with `-ticks`.
- `namefind` and `addrcount` take a real name or address only from the environment variable `HXD_MATCH` (not a flag, so it stays out of shell history and the process list); `tree` marks rows that equal it. They print only IDs, types, offsets, counts, a validated prefix kind and "equals" markers, never the text or the raw bytes next to it. `tree` prints a folder name only when it is a schema word or a strict probe name (`oc-probe-[a-z0-9-]+`). `fieldcmp` masks every u16 that decodes as a letter or digit in any script.
- Two commands written during this stage were removed after review because they could print real text: `keys` (words common to many objects, which include names and addresses) and `head` (raw payload dump, where the redactor misses CJK text).
- `bytecand` and `ticks` accept only a probe target (a UTF-16 string that starts with the marker, optionally after `RE:`); `ticks` also needs `-ticks` and covers only the last 7 days. `bytecand` leaves out every object that has text at the compared offset.
- Real account addresses and real folder names were typed into `namefind`, `addrcount` and `tree` commands during discovery, so they appear in the local terminal and session transcript (not in the repository, not in tool output). Later runs pass them through `HXD_MATCH`.
- Three incidents during discovery, all fixed in the tool: item-class strings glued to a following name field printed about 150 display names; a hex probe printed part of the user's own name as UTF-16 hex; a misparsed folder entry printed the user's own display name next to probe text.

## Open questions

1. **Deleted messages (v1 ships with a per-message `confirmed` flag):** find where the about 3,250 overflow entries of the block index are stored, or the slot hash; then live = in the index. Until then the reader cannot tell a deleted message whose last copy still sits in a block from a live one in an overflow bucket.
2. Attachment content type and an inline-image marker in `0x168`; the meaning of the other length-table entries (+1636, +1644, +1668, +1500).
3. Type-16 block format (not LZ4; probably a journal).
4. Roles of slots +621, +1397, +1445 (Conversation History, Snoozed and one folder the UI does not show); folder IDs of form 2 records (only empty folders so far); which of index areas A and B is current.
5. Account type (Exchange, Outlook.com, IMAP) and the layout of the shared settings object `0x4007`.
6. Attachment content type; Bcc on a probe; meaning of the time at item +624.
7. Which of the two `EFMData` files of a message holds the displayed body.
8. The Junk Email unread difference: does the UI read a stored per-folder count?
9. Meaning of status bits `0x80` and `0x10`, and of the new `0x04` object after a move.
